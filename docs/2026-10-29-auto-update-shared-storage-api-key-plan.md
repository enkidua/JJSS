# 계획안: 자동 업데이트 · 공유 저장소(구글 스프레드시트) · API 키 오류 표시

작성일 2026-10-29. 대상 버전: JJSS 3.1.0 이후(3.2 / 4.0). 이 문서는 구현 전 계획이며, 각 단계는 기존 원칙(DB 구조·공식 서식·수당 단가 불변, 실패 시 기존 데이터 보존, 비식별화 없이는 외부 전송 없음)을 지킨다.

## 0. 한 줄 결론

| 요구 | 기술적 가능 여부 | 권고 |
|---|---|---|
| A. 자동 업데이트 | **가능.** Windows는 자동 내려받기·설치까지, macOS는 서명·공증 전까지 "알림 + 수동 내려받기" | 3.2에 넣는다. 위험이 낮고 효과가 크다 |
| B. 기관 공유 드라이브에 사례관리를 공유 저장(선택 기능) | **가능.** 공유 드라이브 파일 + 오프라인 우선 동기화 + 기록 단위 버전 충돌 처리. 암호문만 올리는 종단간 암호화 기본. 켤 때 보안 안내·자동 점검, 색인·증분·지연 로딩으로 성능 확보 | 설계·시범 운영을 거쳐 4.0. 기관 결재·관리 콘솔 설정이 선행 |
| C. API 키를 잘못 넣었을 때 정확한 오류 표시 | **가능, 쉬움.** 키 형식 판별 + 저장 직후 자동 연결 확인 + 사용 중 실패 원인 안내 | 3.2에 가장 먼저 넣는다 |

## A. 자동 업데이트

### 현재 상태
- `package.json`의 `build.publish`가 `null`이다. 앱에 업데이트 확인 코드가 없다.
- Windows 설치파일은 코드서명(CN=JJSS, 타임스탬프)이 되어 있다. macOS는 임시(ad-hoc) 서명만 있다.
- 배포는 GitHub 저장소 `enkidua/JJSS`의 Releases로 해 왔다.

### 설계
1. **배포 채널:** GitHub Releases를 그대로 쓴다. electron-builder의 `publish: { provider: 'github', owner: 'enkidua', repo: 'JJSS' }`를 두되, **빌드 때 자동 게시는 하지 않는다**(`--publish never`). 검증을 마친 설치파일과 electron-builder가 함께 만드는 `latest.yml`(Windows)·`latest-mac.yml`을 Releases에 올리는 것은 사람이 한다. 초안(draft) 릴리스로 올려 확인한 뒤 공개하면 사용자에게는 공개 시점에 보인다.
2. **앱 쪽(electron-updater):**
   - 시작 10초 뒤와 이후 6시간마다 `checkForUpdates`. 업데이트가 있으면 **먼저 알림만** 띄운다("새 버전 3.2.0이 있습니다 — 지금 받기 / 나중에"). 작업 중 갑자기 내려받지 않는다.
   - 내려받기는 사용자가 누를 때만. 내려받기가 끝나면 "다시 시작하면 설치됩니다" 안내. 설치는 앱 종료 시(`autoInstallOnAppQuit`)에 한다. 미저장 보호(12차)와 같은 확인을 거친 뒤에만 종료한다.
   - 복원(백업 불러오기)·설치파일 생성·AI 요청이 진행 중이면 설치를 미룬다.
   - 서명 검증: electron-updater는 Windows에서 내려받은 설치파일의 서명이 현재 실행 파일의 서명자와 같은지 확인한다(`verifyUpdateCodeSignature`). 우리 인증서 CN=JJSS로 고정한다. HTTPS·GitHub 외의 주소는 쓰지 않는다. 사용자가 업데이트 주소를 바꿀 수 있는 설정은 두지 않는다.
   - 업데이트 확인은 버전 번호와 운영체제만 보낸다. 업무 데이터·API 키는 보내지 않는다. 이 사실을 `PRIVACY_SECURITY.md`의 외부 통신 표에 적는다.
3. **macOS:** Squirrel.Mac은 Developer ID 서명·공증이 없으면 설치를 거부한다. 따라서 Apple Developer Program(연 99달러)에 가입하기 전까지는 **알림만** 하고 "내려받기 페이지 열기"로 안내한다. 가입 후에는 `electron:build:mac`에 서명·공증(`notarize`)을 붙이고 Windows와 같은 흐름으로 바꾼다.
4. **데이터 호환:** 업데이트 뒤 첫 실행에서 DB_VERSION·암호화 이관(기존 `legacyMigration`·`PostRestoreNotice`)이 돈다. 업데이트 직전에 **자동 백업을 한 번 만들어** `JJSS/백업/업데이트전-<버전>-<날짜>.jjss`로 남긴다(복원은 기존 기능으로). 이것이 롤백 수단이다.
5. **되돌리기:** 문제가 있는 버전은 Releases에서 내리고(또는 `latest.yml`을 이전 버전으로 되돌리고) 이전 설치파일을 다시 올린다. electron-updater는 더 낮은 버전으로는 자동 내려가지 않으므로, 사용자는 이전 설치파일을 직접 설치한다. 안내문을 문서에 둔다.

### 검증
- `scripts/test-electron-startup.cjs`에 "업데이트 확인은 작업 중 설치를 시작하지 않는다", "서명자 불일치 설치파일은 거부" 단위 검사.
- 실제 검증: 테스트용 GitHub 저장소(또는 로컬 HTTP 서버를 `provider: generic`으로)에 3.1.0 → 3.1.1을 올려 설치본에서 알림 → 내려받기 → 종료 설치 → 데이터 보존 확인.
- 전체 `verify:release` 통과.

### 공수와 위험
- 약 3~4일. 위험: 낮음(알림 우선, 설치는 종료 시, 서명 검증).

## B. 기관 워크스페이스 공유 드라이브를 사례관리 공유 저장소로 (선택 기능)

### 전제(2026-10-29 확정)
- 기관은 Google Workspace for Nonprofits에 등록되어 있다. **공유 드라이브** 하나(또는 팀별 여러 개)를 만들고, 기관 도메인의 여러 계정이 그 공유 드라이브를 함께 쓴다. 개인 Gmail은 쓰지 않는다.
- 목적은 사례관리 기록을 공유 드라이브에 한곳에 저장해 여러 직원이 각자 맡은 이용자를 같은 저장소에서 다루는 것이다. 같은 기록을 동시에 고치는 일은 드물다.
- **선택 기능이다.** 기본값은 꺼짐이며, 끄면 지금처럼 PC 안에만 저장하고 구글로 가는 요청은 0건이다. 켤 때는 보안 안내와 자동 점검을 거친다.
- 범위는 사례관리(이용자 기본정보, 사례문서 — 직업평가·지원고용·면접일지·직무분석지 포함)부터. 직업훈련·예산·자료수집은 2단계.
- 저장 단위는 스프레드시트가 아니라 **드라이브 파일**이다(셀 제한·사진 불가·요청 한도 문제가 없고, 파일마다 수정 이력과 수정자가 남는다).

### B-1. 선택 기능으로 동작하는 방식
- 설정에 **"공유 저장소(기관 드라이브)"** 탭을 둔다. 스위치 하나로 켜고 끈다.
- **꺼짐(기본):** 코드 경로가 아예 실행되지 않는다. CSP `connect-src`에 구글 드라이브 주소를 넣되, 동기화 모듈이 켜짐 상태가 아니면 요청을 만들지 않는다. `verify:release`에 "꺼진 상태에서 구글 요청 0건" 검사를 넣어 보증한다.
- **켜짐:** 아래 B-2 설정 마법사를 끝낸 PC만 동기화한다. 마법사를 끝내지 못하면 스위치는 켜지지 않는다.
- **끄기:** 끄면 PC 안의 데이터는 그대로 남고 동기화만 멈춘다(드라이브의 파일은 지우지 않는다). 다시 켜면 마지막 동기화 지점부터 이어 받는다. "이 PC의 드라이브 로그인 해제"는 별도 버튼(토큰·기관 키 삭제).
- 기존 백업·복원·암호화·비식별화는 켜짐/꺼짐과 무관하게 지금 그대로다.

### B-2. 처음 켤 때 — 보안 안내와 자동 점검(설정 마법사)
마법사는 다음 순서로 진행하며, 각 단계를 통과해야 다음으로 간다.

1. **안내 화면(읽고 확인):** 무엇이 드라이브에 올라가는지(암호화된 사례관리 기록·첨부), 무엇이 올라가지 않는지(API 키, 기관 키, 비식별화 대응표, 직업훈련·예산은 2단계 전까지 제외), 누가 볼 수 있는지(공유 드라이브 구성원만, 내용은 기관 키가 있는 PC에서만 복호화), 책임(기관 개인정보 처리방침에 포함돼야 함). "기관 결재를 받았습니다" 확인란.
2. **관리자 설정 점검표(관리자용 문서 `docs/SHARED_DRIVE_SETUP.md`로 분리):**
   - 관리 콘솔: 드라이브 **외부 공유 금지**(도메인 밖 공유·링크 공유 차단), **2단계 인증 강제**, 드라이브 감사 로그 보존, 필요하면 Vault.
   - 공유 드라이브: 구성원은 **그룹**(예: 고용지원팀)으로 넣고, 역할은 "콘텐츠 관리자" 이하(관리자 역할은 담당자 1~2명). "구성원이 아닌 사용자에게 공유" 옵션 끄기, "뷰어·댓글 작성자의 다운로드·인쇄·복사" 끄기.
   - GCP 프로젝트(기관 계정 소유): Drive API 켜기, OAuth 동의 화면 **내부**, 클라이언트 ID 발급. 관리 콘솔 "API 접근 제어"에서 이 앱만 신뢰.
3. **기관 로그인:** 시스템 브라우저로 기관 계정 로그인(PKCE). 권한 범위는 `drive.file`(앱이 만든 파일만). 도메인이 기관 도메인이 아니면 거부.
4. **앱의 자동 보안 점검(통과해야 켜짐):** 선택한 드라이브가 **공유 드라이브**인지, 링크 공유가 꺼져 있는지, 구성원 수와 외부 도메인 계정 유무, 드라이브 제한 설정(`driveMembersOnly`, 다운로드 제한), 로그인 계정이 구성원인지. 결과를 "통과 / 주의 / 차단" 표로 보여 주고, 차단 항목이 있으면 켜지지 않는다. 이 점검은 **이후 매일 1회와 동기화 시작 때마다** 다시 돌고, 상태가 나빠지면(예: 누군가 링크 공유를 켬) 동기화를 멈추고 경고한다.
5. **기관 키:** 첫 PC는 기관 키를 만들고 **QR·12단어 구절**로 표시한다(화면에서만, 파일 저장 안 함). 다음 PC들은 QR을 찍거나 구절을 입력한다. 키는 OS 보안 저장소에만 둔다. 메일·메신저로 보내지 말라는 경고와, 잃어버리면 복구가 불가능하다는 경고(기관 키 사본을 봉투에 넣어 금고 보관 권고).
6. **기존 데이터 올리기(첫 동기화):** 이 PC에 그동안 쌓인 사례관리 기록을 지정한 공유 드라이브로 올리는 단계다. 다른 PC에서 이어서 일할 수 있게 하는 핵심이므로 별도 화면으로 둔다.
   - **올리기 전 요약:** 올라갈 것(이용자 N명, 사례문서 N건 — 종류별 건수, 첨부 N개·용량)과 **올라가지 않는 것**(직업훈련·예산·자료수집은 2단계 전까지 PC에만, API 키·기관 키·비식별화 대응표는 절대 안 올라감)을 먼저 보여 주고 확인을 받는다.
   - **자동 백업:** 올리기 직전에 `.jjss` 백업을 만들어 `JJSS/백업/공유저장소-시작전-<날짜>.jjss`로 남긴다. 실패하면 올리기를 시작하지 않는다.
   - **드라이브 상태에 따라:**
     - 드라이브가 비어 있으면 → 이 PC가 기준. 전부 올린다.
     - 드라이브에 이미 기록이 있으면(다른 PC가 먼저 올림) → **합친다.** 같은 ID는 수정 시각이 늦은 쪽을 두고 다른 쪽을 충돌 목록에 넣는다. ID가 달라도 같은 사람으로 보이는 이용자(이름+관리번호가 같음 — 일괄 등록의 중복 규칙과 같다)는 "같은 사람입니까?" 목록으로 보여 주어 사용자가 합치거나 따로 둔다. 자동으로 합치지 않는다.
   - **진행과 중단:** 진행률(건수·용량)을 보여 주고, 중간에 창을 닫거나 인터넷이 끊기면 **올라간 것은 남기고 다음에 이어서** 올린다(아웃박스가 남은 것을 기억). 실패한 항목은 목록으로 보여 주고 "다시 올리기".
   - **올린 뒤 검증:** 드라이브의 색인과 PC의 기록 수·각 기록의 내용 지문(contentHash)을 비교해 "N건 모두 올라감"을 확인한 뒤에야 동기화를 켠다. 하나라도 다르면 켜지 않고 차이를 보여 준다.
   - **옛 기록 보정:** 기존 기록에는 `version`이 없으므로 올리면서 1을 채운다(PC의 DB_VERSION 이관과 같은 시점). 읽지 못한 암호문(보안 키 문제)이 있는 기록은 올리지 않고 건너뛴 목록에 넣는다 — 깨진 데이터를 공유 저장소에 퍼뜨리지 않기 위해서다.
   - **다른 PC에서 이어서 일하기:** 두 번째 PC는 같은 마법사에서 기관 로그인·기관 키 입력 뒤 "드라이브에서 받아오기"를 고른다. 그 PC에 이미 기록이 있으면 위와 같은 합치기 규칙을 적용한다. 받아온 뒤부터는 두 PC 모두 B-4의 동기화로 같은 저장소를 쓴다.

### B-3. 저장 구조·인증·암호화
- 공유 드라이브 안 구조:
  ```
  JJSS 사례관리(공유 드라이브)
  ├─ _meta/     manifest.jjss.enc(색인: 기록 id·종류·버전·수정시각·검색용 이름/관리번호 — 전체 암호화)
  │             schema-version.json, security-check.json(마지막 점검 결과)
  ├─ seekers/   <seekerId>.jjss.enc
  ├─ documents/ <yyyy>/<documentId>.jjss.enc        연도 폴더(아래 성능 항목)
  └─ attachments/ <documentId>/<fileId>.enc         사진·첨부(암호화, 필요할 때만 내려받음)
  ```
- 파일 내용은 PC에서 AES-GCM으로 암호화한 암호문. 드라이브 `appProperties`에는 `kind`, `version`, `updatedAt`, `updatedBy`, `deleted`만 평문. 파일 이름에 이용자 이름 없음.
- **종단간 암호화를 기본으로 한다.** 워크스페이스 통제는 "누가 닿는가"를 막고, 암호화는 "닿아도 못 읽게" 한다. 기관이 드라이브 화면에서 내용을 직접 보길 원하면 평문 저장 옵션을 둘 수 있으나 기본값은 아니며, 켜려면 마법사에서 위험을 읽고 별도 확인해야 한다.
- 인증 토큰과 기관 키는 지금 API 키와 같은 OS 보안 저장소(DPAPI·키체인)에 보관. 기관 키 회전(퇴사 시 교체 → 전체 재암호화 → 옛 키 폐기)을 1차 범위에 포함.

### B-4. 동기화와 동시 수정
- **오프라인 우선:** 화면은 지금처럼 PC의 IndexedDB를 읽고 쓴다. 변경은 아웃박스에 쌓였다가 뒤에서 올라간다. 인터넷이 없어도 앱은 그대로 동작하고, 복귀하면 이어서 올린다.
- **받기:** 드라이브 `changes` API의 페이지 토큰을 저장해 두고 **바뀐 파일만** 받는다(폴링 30~60초, 사용자가 "지금 동기화"로 즉시 실행 가능).
- **낙관적 잠금:** 기록마다 `version`. 올리기 전 드라이브의 `version`이 내가 읽은 값과 같아야 올린다. 다르면 "다른 PC에서 먼저 고친 기록"으로 표시하고 두 내용을 나란히 보여 주어 사용자가 고른다(자동 병합 없음).
- **편집 중 표시(soft lock):** 문서를 열면 `appProperties.editingBy/editingSince`를 남겨 다른 PC에 "○○ 담당자가 편집 중"을 보여 준다. 강제 잠금은 아니며 30분 지나면 무시한다(PC가 꺼져도 영원히 잠기지 않게).
- **삭제:** 묘비(`deleted`) 표시 후 30일 뒤 정리. 드라이브 휴지통·버전 기록이 추가 안전망.
- **복원과의 관계:** 백업 복원 시 동기화를 멈추고 "이 PC 복원본으로 드라이브를 덮기 / 드라이브로 이 PC를 덮기"를 고르게 한다. 어느 쪽이든 복원 전 자동 백업을 남긴다.
- **AI 비식별화:** 드라이브로 가는 것은 암호문이라 비식별화 대상이 아니다. 동기화로 받은 이름이 이름 사전에 들어가도록 dataStore 초기화 경로를 동기화 뒤에도 다시 돈다.

### B-5. 데이터가 쌓여도 느려지지 않게 — 성능 설계
드라이브는 "파일 목록 전체를 매번 훑는" 순간부터 느려진다. 처음부터 다음 규칙을 둔다.

| 문제 | 설계 |
|---|---|
| 시작할 때 파일 수천 개를 목록으로 훑으면 수십 초 걸림 | **색인 파일(manifest)** 하나를 먼저 받는다. 전체 기록의 id·종류·버전·수정시각·검색용 이름이 들어 있어 목록 요청 없이 "무엇이 바뀌었는지"를 즉시 안다. 색인은 올리는 쪽이 변경 때마다 갱신(낙관적 잠금 적용). 색인이 깨지면 `changes` API로 다시 만든다 |
| 매번 전체를 다시 받음 | `changes` 페이지 토큰으로 **증분**만. 파일마다 `version`이 PC와 같으면 내려받지 않는다 |
| 첫 PC 설정 때 수천 파일 내려받기 | 동시 요청 6개 한도의 병렬 내려받기 + 진행률 표시. 화면은 막지 않고 **받은 것부터 쓸 수 있게** 한다(이용자 목록이 먼저, 문서 본문은 뒤에). 목표: 사례문서 5,000건 첫 동기화 3분 이내(100Mbps 기준) |
| 사진·첨부가 큼 | **열 때만** 내려받는다(지연 로딩). 색인에는 크기·개수만. PC 캐시는 최근 사용 순으로 2GB 상한 |
| 오래된 기록이 계속 늘어남 | **연도 폴더**(`documents/2024/…`)와 "활성 기간" 설정(기본 최근 2년). 그보다 오래된 기록은 색인에는 있되 본문은 열 때 받는다. 종결 5년 이상 기록은 관리자 기능으로 `archive/`로 옮기고 기본 동기화에서 제외(보존 기간 정책은 기관 규정에 따름) |
| 요청 한도(사용자당 분당 수백 회) | 변경을 **묶어서** 올리고(배치), 폴링 간격을 바꿀 수 있게. 429 응답이면 지수 대기 후 재시도 |
| 공유 드라이브 항목 수 상한(40만 개) | 파일 하나 = 문서 하나이므로 수만 건까지 여유. 첨부가 많아지면 연도별 공유 드라이브로 나눌 수 있게 구조를 둔다 |
| 색인을 여러 PC가 동시에 갱신 | 색인도 `version` 낙관적 잠금. 실패하면 다시 받아 합친 뒤 재시도(최대 3회), 그래도 안 되면 다음 동기화로 미룸 |
| PC 안 검색 | 검색은 IndexedDB(지금 구조)에서. 드라이브에 질의하지 않는다 |

성능 검증은 합성 데이터 10,000건(이용자 500명·문서 9,500건·첨부 2GB)으로 첫 동기화·증분 동기화·시작 시간·메모리를 재는 `scripts/test-sync-performance.mjs`를 두고, 목표치(첫 동기화 3분, 증분 3초, 앱 시작 지연 0초 — 동기화는 시작을 막지 않음)를 문서에 고정한다.

### B-6. 운영 요건(관리자)
- 비영리 요금제에서 공유 드라이브를 쓸 수 있는지 확인(안 되면 기관 소유 폴더로 대체 가능하되 퇴사 처리가 번거로움).

## C. API 키 오류를 정확히 표시

### 지금 생기는 문제
- OpenAI 칸에 Gemini 키(`AIza…`)를 넣어도 저장은 된다. 연결 확인은 **버튼을 눌러야만** 돌고, 누르지 않으면 실제 문서 작성 때 "API 키가 올바르지 않습니다"만 보고 어느 칸이 잘못됐는지 알기 어렵다.
- 실패 원인 분류(`connectionCheck.ts`: 키 오류·권한·할당량·네트워크·시간 초과·모델·서비스)는 이미 있다. 빠진 것은 **입력 시점 판별**과 **자동 확인**, 그리고 **사용 중 실패 → 설정으로 안내**다.

### 설계
1. **키 형식 판별(입력 즉시, 네트워크 없음):**
   - Google(Gemini·Vision): `AIza`로 시작, 39자.
   - OpenAI: `sk-`로 시작(`sk-proj-` 포함), `sk-ant-`는 제외.
   - Anthropic: `sk-ant-`로 시작.
   - 다른 제공업체 형식이 들어오면 저장을 막지는 않되 칸 아래에 즉시 표시: "이 키는 Google(Gemini) 키 형식입니다. OpenAI 칸에 넣으면 동작하지 않습니다. [Gemini 칸으로 옮기기]". 버튼 하나로 올바른 칸에 넣어 준다.
   - 앞뒤 공백·줄바꿈·따옴표·"Bearer " 접두어는 저장 전에 지우고 그 사실을 알린다.
   - 형식이 어느 제공업체와도 맞지 않으면 "발급받은 키 전체를 복사했는지 확인" 안내.
2. **저장 직후 자동 연결 확인:** 키를 저장하면 그 칸의 연결 확인을 자동으로 돈다(지금의 `checkProviderConnection`, 업무 내용 전송 없음, 20초 제한). 결과를 칸 옆에 **상태 표지**로 남긴다: 확인됨(시각) / 실패(원인 한 줄) / 미확인. 상태는 설정에 저장해 다음 실행에도 보이게 한다(키 자체가 바뀌면 "미확인"으로).
3. **실패 원인 메시지를 칸 기준으로:** 지금 메시지에 "어느 칸의 키"인지와 "다음에 할 일"을 붙인다. 예: "OpenAI 칸의 키가 거부됐습니다(401). 키가 Google 형식(AIza…)이라 OpenAI에서는 쓸 수 없습니다. → Gemini 칸으로 옮기기" / "Claude 칸의 키는 맞지만 결제 수단이 없어 거부됐습니다(credit). → Anthropic 콘솔에서 결제 확인".
4. **사용 중 실패 안내:** 문서 작성 중 인증 오류가 나면 토스트에 "설정에서 확인"을 넣고 누르면 해당 칸으로 바로 이동(설정 화면의 섹션 이동은 이미 있음). 같은 키로 연속 실패하면 그 제공업체의 상태 표지를 "실패"로 바꾸고, 자동 전환(failover) 후보에서 제외한다는 안내.
5. **제공업체 선택 칸과의 정합:** 선택한 제공업체의 키가 "실패" 상태면 설정 상단에 경고 띠를 띄운다. 키가 없는 제공업체를 선택하면 저장 전에 알린다.
6. **온보딩 창(첫 실행):** 같은 형식 판별을 적용하고, "저장하고 시작"을 누르면 자동 확인 결과를 보여 준 뒤 넘어간다.

### 검증
- `scripts/test-ai-settings.mjs`: 형식 판별 표(각 제공업체 키 → 판별 결과, 공백·따옴표 제거, 교차 입력 경고), 자동 확인 호출 1회, 상태 표지 저장/복원.
- `test-usability.cjs`: OpenAI 칸에 `AIza…` 합성 키 입력 → 경고 문구와 "옮기기" 버튼 → 누르면 Gemini 칸에 들어가고 OpenAI 칸은 비는지.
- 연결 확인은 지금처럼 업무 내용을 보내지 않음을 `test-ai-request-safety.mjs`로 유지.

### 공수와 위험
- 약 2일. 위험: 낮음.
